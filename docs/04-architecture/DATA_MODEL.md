# Model data PostgreSQL — PRANATA UNY

Status: P4 candidate — VERIFYING (AUTH-012), belum disetujui | Updated: 2026-10-30 (Asia/Jakarta) | Custodian: Planning Agent | Phase: P4

Dokumen ini memiliki **skema logis-implementasi PostgreSQL**: konvensi, tabel per modul, kolom, constraint, indeks, partisi, peran basis data dan aturan migrasi. Makna konsep tetap dimiliki P2 ([DOMAIN_GLOSSARY](../02-domain/DOMAIN_GLOSSARY.md), [BUSINESS_RULES](../02-domain/BUSINESS_RULES.md)); keadaan dan transisi dimiliki P3 ([STATE_TRANSITIONS](../03-workflows/STATE_TRANSITIONS.md)). Nilai status di bawah adalah kode teknis yang memetakan state P3; kode itu bukan aturan bisnis baru. Eksekutor membuat migrasi sesuai dokumen ini pada Task yang ditunjuk; perubahan material memerlukan TASK PLAN CHANGE dan, bila menyentuh ADR, persetujuan Owner.

## 1. Konvensi

| Hal | Aturan |
|---|---|
| Skema dan nama | Satu basis data `pranata`, skema `public`. Tabel jamak `snake_case` berprefiks modul (`proc_`, `inv_`, `asset_`, …); tabel kerangka Laravel tanpa prefiks. Indeks `<tabel>_<kolom>_idx`, unik `<tabel>_<kolom>_uq`, check `<tabel>_<aturan>_chk`. |
| Kunci | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. Akar agregat yang tampil di URL memiliki `public_id char(26) NOT NULL UNIQUE` (ULID dibuat aplikasi); URL tidak pernah memuat `id` internal. |
| Waktu | `timestamptz` disimpan UTC; tampilan Asia/Jakarta. Tanggal bisnis memakai `date`; tahun anggaran `smallint`. |
| Uang dan kuantitas | Nilai total `numeric(20,2)`; harga satuan `numeric(20,4)`; kuantitas `numeric(18,4)`; persentase `numeric(9,4)`. Aritmetika aplikasi memakai desimal presisi (brick/math), tidak pernah float. Aturan pembulatan berasal dari kebijakan. |
| Status | `varchar(40)` + `CHECK` daftar nilai; enum PHP sebagai sumber nilai; tanpa tipe ENUM PostgreSQL. |
| Audit kolom | `created_at`, `updated_at`, `created_by`, `updated_by` (FK `users`) pada tabel yang dapat diubah; `lock_version integer NOT NULL DEFAULT 0` pada agregat yang diedit bersamaan. |
| Penghapusan | Tidak ada hard delete record bisnis dan tidak ada `deleted_at`. Draf yang dibuang berstatus `DISCARDED`/`WITHDRAWN`. Penghapusan fisik hanya kelak menurut kebijakan retensi (GAP-023). FK default `ON DELETE RESTRICT`. |
| JSON | `jsonb` hanya untuk snapshot, konfigurasi, metadata dan bukti struktur yang tidak sering difilter. |
| Teks pencarian | Ekstensi `pg_trgm`; indeks GIN trigram pada nama/kode yang dicari. |
| Ekstensi | `pg_trgm`, `ltree`, `btree_gist`. Tanpa ekstensi berbayar/non-standar. |
| Penandaan kebijakan | Record yang dihasilkan dari aturan berversi menyimpan `policy_version_id` dan `is_simulation boolean NOT NULL DEFAULT false`. |
| Penandaan transisi | Setiap perubahan state menulis `workflow_transitions` dengan `transition_code` TR P3. |
| Kebijakan majemuk | Record yang bergantung pada lebih dari satu keluarga kebijakan mencatat setiap versi penyumbang di `policy_version_uses` (bagian 8) dalam transaksi yang sama; kolom `policy_version_id` tetap menunjuk keluarga utama. |
| Konsistensi induk lintas record | Record anak yang merujuk dua induk dalam lingkup yang sama (paket, pemilihan, lingkup penghargaan, kontrak, permintaan, gudang) membawa kolom lingkup itu dan memakai FK komposit `(rujukan, lingkup) → induk(id, lingkup)`; induk menyediakan `uq(id, lingkup)`. Kolom lingkup tidak dapat diubah setelah insert (trigger `forbid_scope_change()`). Bila FK komposit tidak memadai, constraint trigger memeriksa dalam transaksi yang sama. |
| Identitas peristiwa bisnis | Entri ledger yang berasal dari baris sumber membawa `(source_type, source_id, source_line_id)` dengan constraint unik per jenis entri, sehingga satu peristiwa fisik tidak dapat diposting dua kali walaupun kunci idempotensi permintaannya berbeda. Record sumber tidak menyimpan ID entri ledger; entri ditemukan melalui identitas sumbernya. |
| Pembalikan | Paling banyak satu pembalikan per entri asli (`uq(reversal_of_id)`); pembalikan selalu penuh dan diperiksa trigger (entitas, jumlah, arah). Koreksi sebagian dicatat sebagai entri koreksi tersendiri dengan dokumen sumbernya. |
| Baris final beku | Baris anak dari induk yang sudah final tidak dapat diubah atau dihapus (trigger `forbid_change_when_parent_final()`): baris HPS setelah SET, baris penerimaan setelah POSTED, baris opname setelah CLOSED, baris transfer setelah DISPATCHED (kecuali `qty_received` saat penerimaan), baris serah terima gudang sejak diposting, dan baris BAST setelah SIGNED kecuali kolom klasifikasi dan rujukan hilir (WF-016). Baris kontrak append-only per versi. Skema evaluasi beserta tahap, kriteria dan penerapan lingkup kriterianya beku setelah FROZEN — termasuk penolakan baris anak baru (trigger insert memeriksa skema masih DRAFT) — putaran evaluasi beserta hasilnya setelah COMPLETED, peringkat setelah hasil DETERMINED, rekaman penawaran beserta lingkup, rincian harga dan entri pembukaannya imutabel sejak dicatat (INV-023), dan versi batas akhir pemasukan append-only. Perubahan dibuat sebagai versi atau dokumen baru. |
| Satu versi berlaku | Konfigurasi berversi (versi kebijakan, versi template, versi klasifikasi) memiliki paling banyak satu versi disahkan per kunci dan tanggal, ditegakkan `EXCLUDE` atas jendela `[effective_from, effective_to)`; skema penomoran terikat pada versi kebijakan `numbering`-nya (satu skema per jenis dokumen per versi). Aktivasi dan penutupan versi sebelumnya atomik di bawah kunci baris induk; `effective_from` tidak boleh sebelum tanggal aktivasi (tanpa tanggal mundur, [STATE_TRANSITIONS TR-286](../03-workflows/STATE_TRANSITIONS.md#wf-029)). **Keberlakuan resmi** — satu-satunya dasar gerbang aksi resmi — adalah disahkan (ACTIVE atau SUPERSEDED) dan jendela memuat tanggal acuan; kolom `status` sendiri tidak pernah menjadi gerbang, sehingga versi SUPERSEDED tetap dipakai untuk tanggal di dalam jendelanya dan versi terjadwal tidak dipakai lebih awal ([POLICY_REGISTRY §3.1](POLICY_REGISTRY.md#31-keberlakuan-resmi)). |

Notasi kolom di tabel bawah: `→ tabel` berarti FK; `uq` unik; `nn` NOT NULL; nilai dalam kurung kurawal adalah daftar `CHECK`.

| submitted_at, activated_at, retired_at | timestamptz | |
| notes | text | |

`EXCLUDE USING gist (pack_id WITH =, daterange(effective_from, effective_to, '[)') WITH &&) WHERE (status IN ('ACTIVE', 'SUPERSEDED'))` — jendela berlaku versi yang pernah aktif tidak pernah tumpang tindih untuk satu paket. Aktivasi versi baru menutup jendela versi terbuka sebelumnya pada `effective_from` versi baru dan menandainya SUPERSEDED dalam transaksi yang sama, di bawah kunci baris `policy_packs`; `effective_from` tidak boleh sebelum tanggal aktivasi. Versi SUPERSEDED tetap berlaku untuk tanggal acuan di dalam jendelanya; RETIRED tidak pernah dipilih. Keberlakuan resmi (disahkan dan jendela memuat tanggal acuan) ditentukan oleh resolver, bukan oleh `status` ([POLICY_REGISTRY §3.1](POLICY_REGISTRY.md#31-keberlakuan-resmi)). Trigger `guard_version_transition()` — dipasang juga pada versi template dan versi klasifikasi — hanya mengizinkan DRAFT ↔ IN_REVIEW, IN_REVIEW → ACTIVE atau REJECTED, ACTIVE → SUPERSEDED (hanya bersama aktivasi penerus) atau RETIRED; SUPERSEDED, RETIRED dan REJECTED final; `effective_from`, `content` dan bukti tidak berubah sesudah ACTIVE, dan `effective_to` hanya diisi oleh aktivasi penerus. Dengan begitu status disahkan tidak dapat dicapai lewat UPDATE langsung tanpa aktivasi berbukti. Pemetaan ke keadaan WF-029 ada di [POLICY_REGISTRY §2](POLICY_REGISTRY.md#2-lifecycle-versi).

## 11. Numbering

**numbering_schemes** — `id`, `code varchar(60) uq`, `document_type varchar(60) nn`, `policy_version_id → policy_versions nn`, `pattern varchar(200) nn` (misalnya `{seq:4}/{unit}/{doc}/{year}`), `scope_keys jsonb nn`, `reset_rule {YEARLY, NEVER}`, `gapless boolean nn`, `sequence_key varchar(80) nn` (identitas penghitung; skema versi-versi kebijakan yang memakai `sequence_key` sama melanjutkan satu penghitung), `status {ACTIVE, RETIRED}` (RETIRED = ditarik karena salah sebelum dipakai; bukan cara berganti skema); `uq(document_type, policy_version_id) WHERE status = 'ACTIVE'` — paling banyak satu skema per jenis dokumen untuk setiap versi kebijakan `numbering`; `uq(id, document_type)`; `uq(id, document_type, sequence_key)`; `document_type`, `policy_version_id` dan `sequence_key` tidak dapat diubah. Skema yang dipakai untuk finalisasi adalah skema jenis dokumen itu pada versi kebijakan `numbering` yang berlaku resmi pada tanggal finalisasi ([POLICY_REGISTRY §3.1](POLICY_REGISTRY.md#31-keberlakuan-resmi)); pergantian skema terjadi karena versi kebijakan penerus mulai berlaku, sehingga skema versi terjadwal tidak dipakai lebih awal dan skema pendahulu tetap dipakai sampai tanggal itu. Kesinambungan nomor urut lintas versi mengikuti isi kebijakan (GAP-017) melalui `sequence_key`: kunci sama melanjutkan penghitung yang sama (tanpa reset di tengah tahun), kunci baru memulai penghitung baru hanya bila kebijakan menyatakannya; apa pun pilihannya, tabrakan ditolak `uq(document_type, number_text)`.

**numbering_counters** — `id`, `document_type varchar(60) nn`, `sequence_key varchar(80) nn`, `scope_key varchar(200) nn`, `next_value bigint nn`, `uq(document_type, sequence_key, scope_key)`. ### 14.3 Pemilihan

Bagian ini mewujudkan [OD-35](../00-governance/DECISION_LOG.md#od-35) dan [OD-36](../00-governance/DECISION_LOG.md#od-36) (BR-036–BR-038, INV-023/024): paket dibagi menjadi **lingkup penghargaan** (seluruh paket, lot atau item); setiap **pemilihan** mencakup satu atau lebih lingkup dengan satu penetapan metode; penawaran asli imutabel; **skema evaluasi** dari dokumen pengadaan dibekukan sebelum pembukaan; hasil, peringkat, pemenang dan cadangan dicatat **per lingkup**; SPPBJ dan kontrak dibuat per pemenang atas lingkup yang dimenanginya. Rantai lingkup dijaga FK komposit, bukan hanya aplikasi. Paket tanpa pembagian memakai satu lingkup PACKAGE sehingga berperilaku satu pemenang per paket. Bentuk alur per metode (langkah mana yang berlaku) berasal dari rencana langkah dan kebijakan, bukan dari tabel ini: Pengadaan Langsung dapat memakai penjajakan, penawaran dan negosiasi tanpa pembukaan formal; Quotation, Tender dan Penunjukan Langsung memakai undangan/pengumuman, pembukaan, evaluasi dan berita acara; E-Purchasing memakai opsi katalog dan negosiasi tanpa penawaran atau pembukaan.

**Invarian batas akhir, pembukaan dan kelayakan evaluasi.** Waktu disimpan sebagai `timestamptz` dan ditampilkan dalam WIB. Kiriman berbatas **tepat waktu** terhadap batas (*c*, *i*) bila `received_at < c`, atau *i* benar dan `received_at = c`. PR 34/2023 menolak penawaran yang masuk setelah batas akhir pemasukan (Lampiran III B.3.b.4; III.C.4.b.1.e; III.D.2.b.4); perlakuan penerimaan tepat pada saat batas belum tervalidasi (GAP-017/029), sehingga *i* berasal dari kebijakan dan tersimpan pada versi batas akhir. Penegakan:

1. Setiap sampul berbatas mempunyai batas akhir tercatat sebelum kiriman pertamanya dan sebelum dibuka atau ditutup. Catatan pembukaan/penutupan membekukan batas akhir yang berlaku untuk sampulnya dan untuk setiap sampul lain di pemilihan yang batasnya tidak lebih lambat dari `cutoff_at` catatan itu, serta menyalin `cutoff_at`/`cutoff_inclusive` melalui FK; `CHECK` pada entri pembukaan memakai salinan `received_at` kiriman, sehingga kiriman terlambat tidak pernah mempunyai entri.
2. Constraint trigger tertunda `check_opening_consistency()` — dipasang pada catatan pembukaan, entri, insert kiriman dan perubahan status kiriman — memastikan saat commit, untuk setiap pemilihan dan sampul yang mempunyai catatan RECORDED: setiap kiriman berbatas yang tepat waktu dan tidak mundur mempunyai entri dan berstatus OPENED atau NOT_OPENED sesuai `opened`; setiap kiriman terlambat tidak mempunyai entri dan berstatus REJECTED_LATE; kiriman WITHDRAWN_BEFORE_DEADLINE tidak mempunyai entri (ketepatan waktu penarikannya diperiksa `forbid_offer_change()` saat transisi); tidak ada yang tetap RECEIVED. Untuk sampul tanpa catatan RECORDED, tidak ada kiriman berstatus OPENED atau NOT_OPENED, dan REJECTED_LATE hanya bila batas sampul itu sudah beku dan kiriman terlambat terhadapnya. Untuk setiap peserta dan sampul, paling banyak satu kiriman berstatus RECEIVED, OPENED atau NOT_OPENED yang tepat waktu terhadap batas akhir yang berlaku (juga diperiksa saat versi batas akhir baru dicatat), sehingga pembukaan tidak pernah terkunci oleh kiriman ganda.
3. Trigger insert kiriman berbatas mengunci baris `proc_selections`, menolak kiriman untuk sampul yang belum mempunyai versi batas akhir, dan menerima kiriman baru hanya berstatus RECEIVED, kecuali REJECTED_LATE bagi kiriman terlambat terhadap batas yang sudah beku. Bila batas sampulnya sudah beku, kiriman tepat waktu ditolak (perbaikan hanya melalui penggantian catatan pembukaan yang membekukannya, selama belum ada hasil evaluasi yang merujuk catatan itu; sesudahnya menjadi pengecualian di luar sistem yang memerlukan keputusan berwenang). Kiriman tepat waktu kedua dari peserta yang sama untuk sampul yang sama wajib merujuk kiriman yang digantinya (`supersedes_id`, bila dokumen pengadaan mengizinkan penggantian); kiriman terlambat tidak pernah menggantikan.
4. Hasil kriteria dan hasil tahap yang dinilai merujuk entri pembukaan dengan `opened = true` melalui FK; klarifikasi dan negosiasi mensyaratkan penawaran OPENED (constraint trigger). Kiriman terlambat, mundur atau tidak dibuka tidak dapat dievaluasi, diklarifikasi atau dinegosiasikan.
5. Pengecualian yang diizinkan kebijakan (misalnya perpanjangan karena gangguan) hanya berupa versi batas akhir EXTENSION_DECISION yang tercatat dengan pengambil keputusan, penugasan, alasan dan bukti, dan hanya sebelum batas sampul itu beku. Tidak ada jalur aplikasi atau basis data untuk mengubah ketepatan waktu satu kiriman secara langsung.
6. Waktu yang berasal dari bukti eksternal (waktu terima, waktu penarikan, waktu terbit dokumen dasar) tidak dapat diverifikasi basis data; risikonya dimitigasi bukti berkas wajib, jam basis data pada `recorded_at`/`withdrawal_recorded_at`, audit, dan penandaan pencatatan yang terjadi sesudah batas lewat.

Pemetaan P3: status kiriman adalah kode teknis di dalam WF008-S2 (diterima) dan WF008-S4 (hasil tercatat). REJECTED_LATE mencatat fakta bahwa waktu terima melewati batas akhir tercatat sehingga kiriman tidak dibuka atau dievaluasi; penolakan resmi tetap TR-076 yang BLOCKED_BY_GAP (GAP-003/014/017), sehingga record resmi hanya ada bila versi kebijakan yang berlaku resmi menetapkan perlakuan batas akhir dan fungsi penolaknya — selain itu keluarannya simulasi (INV-022).

**Penerapan kriteria per lingkup.** `scope_id` pada hasil kriteria dan hasil tahap kosong tepat bila tahapnya per peserta (`CHECK (per_scope = (scope_id IS NOT NULL))` atas salinan `per_scope` yang dijaga FK); tahap per lingkup selalu memakai lingkup eksplisit, termasuk lingkup PACKAGE tunggal. Hasil kriteria per lingkup hanya untuk lingkup yang tercantum pada penerapan kriteria itu (FK `(criterion_id, scope_id)`) dan yang ditawar peserta (FK `(submission_id, scope_id)`); hasil tahap per lingkup hanya untuk lingkup yang mempunyai kriteria tahap itu yang berlaku. Kegagalan tahap gugur per peserta menghentikan penilaian tahap berikutnya pada semua lingkup peserta itu; kegagalan tahap gugur per lingkup hanya pada lingkup itu. Aplikasi tidak membuat skor, bobot atau ambang; semuanya berasal dari dokumen pengadaan.

## 19. Aturan migrasi

1. Setiap perubahan skema lewat migrasi Laravel berurutan, dapat direview, dijalankan dengan koneksi `migrator`; aplikasi memakai `pranata_app`.
2. Pola expand–contract untuk perubahan pada tabel berisi data; tidak ada perubahan destruktif tanpa cadangan terverifikasi, rencana rollback dan persetujuan rilis (P10).
3. Transformasi data dilakukan oleh command terpisah yang idempoten, dapat dijalankan ulang dan diuji pada salinan sintetis; tidak pernah oleh agen terhadap produksi ([PRODUCTION_DATA_SAFETY](../00-governance/PRODUCTION_DATA_SAFETY.md)).
4. Uji migrasi di CI: `migrate:fresh` penuh, `migrate:rollback` untuk migrasi baru yang reversibel, dan pemeriksaan hak peran `pranata_app` pada tabel append-only.
5. Kolom FK ke tabel yang dibuat oleh Task kemudian ditambahkan oleh migrasi Task pemilik tabel tujuan, bukan dibuat lebih awal tanpa FK: `evidence_file_id` pada `org_appointments` dan `process_assignments` ditambahkan saat `file_objects` dibuat; `amendment_id` pada `proc_contract_versions` (beserta `CHECK` dan unique pasangannya) saat `proc_amendments` dibuat; `last_depreciation_period` dan `last_depreciation_run_id` pada `asset_assets` saat `asset_depreciation_runs` dibuat; `award_scope_id` pada `proc_package_items` saat `proc_award_scopes` dibuat; `handover_id` pada `proc_inspections` saat `proc_handovers` dibuat.
6. Fungsi trigger generik (`forbid_update_delete()`, `forbid_scope_change()`, `forbid_change_when_parent_final()`) dibuat sekali bersama fondasi audit; fungsi khusus ledger (`check_stock_reversal()`, `check_asset_reversal()`, `check_movement_source_<jenis>()`) dibuat bersama tabel ledger atau tabel sumbernya. Pemasangan dilakukan oleh migrasi Task pemilik tabel; setiap pemasangan disertai uji negatif langsung ke basis data ([TEST_STRATEGY §10](../08-testing/TEST_STRATEGY.md#10-skenario-integritas-data-wajib)).
7. Seeder hanya memuat data referensi teknis, kebijakan **DRAFT** beserta rujukan sumber, dan data sintetis untuk non-produksi; tidak ada data pribadi atau data transaksi riil.
